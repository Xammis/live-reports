Agency architecture decision

The Case Against Headless WordPress but For Static

For Xammis running 20+ websites with 2+ developers, the best system is usually the one with fewer moving parts, clear environments, and less deployment drama.

Headless reality20 sites → 40 apps
Best defaultTraditional WP
Hidden middle pathStatic export
Against headless as default

Headless usually makes agency operations harder

  • Each website has a WordPress backend plus a separate frontend app.
  • More deployment pipelines, environments, and drift between local, dev, staging, and production.
  • Preview, redirects, routing, caching, media, auth, CORS, and plugin compatibility become custom work.
  • Editors can lose native WordPress conveniences unless the team rebuilds them.
  • 20 websites can quietly become 40 deployable systems.
For traditional WP

The boring baseline is strong

  • Clients get the normal WordPress editing experience.
  • Developers can standardize DDEV, Local, or Lando.
  • Git manages themes, plugins, mu-plugins, Composer, and config.
  • Dev/staging/prod workflows are familiar and easier to train.
  • Managed WP hosting or VPS automation keeps operations predictable.
Operational model

Traditional WordPress agency workflow

LOCALDDEV / Local / Lando per developer
GITTheme, plugin, Composer, config changes
DEVShared integration environment
STAGINGClient review and QA
PRODBackups, monitoring, managed deploys

Key rule: content flows down, code flows up. Use WP Migrate, host tooling, or scripted syncs for database and uploads.

For static WordPress

Static can flatten production

Use WordPress as the private CMS/editor, then publish the public site as static HTML to Cloudflare Pages, Netlify, S3, or similar.

  • Fast, secure, and cheap to host.
  • No public PHP/MySQL runtime to maintain.
  • Great rollback and deployment story.
  • Excellent for brochure, marketing, and service-business sites.
Static tradeoffs

Dynamic features move elsewhere

  • Forms need external handling.
  • Search needs a static/client-side approach or service.
  • Comments, memberships, ecommerce, gated content, and personalization may not fit.
  • Preview and publish workflows need discipline.
  • Some plugins cannot be flattened cleanly.

Tier A

Normal client sites

Use traditional WordPress. Standardize environments, hosting, deployment, backups, and sync rules.

Tier B

Simple marketing sites

Offer static WordPress export. Keep WP for content, ship static HTML for production.

Tier C

Premium special cases

Use headless only when the project truly needs app-like frontend power or omnichannel content.

Blunt verdict: for 20+ websites and 2+ developers, headless WordPress is harder. Traditional WordPress is safer. Static WordPress export is the clever third option for simple sites.
